## 1 - Введение

Мы собираемся создать приложение для продажи учебников и конспектов студентам CIP FP Batoi. В качестве инструментов мы будем использовать следующие столы:

- **курсы**: Это различные циклы центра. Их поля: _id_ (автонумерация), _course_ (краткое название цикла), _familyId_ (внешний ключ таблицы families), _vliteral_ и _cliteral_ (полное название на валенсийском и испанском языках).
- **семейства**: профессиональные группы центра (ИТ, здравоохранение, гостиничный бизнес и т. д.). Их поля: _id_ (автономер), _vliteral_ и _cliteral_ (полное название на валенсийском и испанском языках).
- **модули**: различные модули, изучаемые в каждом цикле. Их поля: _code_ (первичный ключ, 4-символьная числовая строка), _courseId_ (внешний ключ из таблицы курсов), _vliteral_ и _cliteral_ (полное название на валенсийском и испанском языках).
- **продажи**: поле, где регистрируются продажи. Его поля: _id_ (автонумерация), _bookId_ (внешний ключ таблицы книг), _userId_ (внешний ключ таблицы пользователей), _date_ (данные о продажах в формате ГГГГ-ММ-ДД) и _status_ (статус продаж, числовое значение).
- **пользователи**: данные пользователей, зарегистрированных в приложении. Поля: _id_ (автонумерация), _nick_, _email_ и _password_.
- **книги**: книги и конспекты на продажу. Категории:
  - _id_ (автонумерация)
  - _userId_: внешний ключ таблицы пользователей
  - _moduleCode_: Внешний ключ таблицы модулей
  - _издатель_: издательство, которое публикует книгу. Если это примечания, их значение — «Апунты».
  - _цена_: цена (числовое значение)
  - _страницы_: страницы книги/заметок (числовые)
  - _status_: статус книги, который может принимать одно из значений: «новая», «хорошая», «б/у» или «плохая». Если это цифровая книга/заметки, ее значение будет «цифровая».
  - _фото_: путь к фотографии
  - _комментарии_: комментарии
  - _soldDate_: Дата продажи книги в формате ГГГГ-ММ-ДД. Если книга еще не продана, это поле будет пустым.

## 2 - Массивы

Первую часть приложения мы будем разрабатывать в ветке '**2-arrays**'. Здесь мы создадим основные функции для работы с нашими данными (напомним, что пока они находятся в файле `datos.js` в переменной с именем _data_). В этом упражнении мы создадим функции для работы с книгами, пользователями и модулями.

Напоминаем, что код находится в отдельных JS-файлах:

- `src/main.js`: это основной модуль, который импортирует остальные, отображает страницу, вызывает функции и выводит данные в консоль.

  — Какие книги пользователь выставил на продажу?
  — А какой конкретный модуль?
  — Какие книги стоят столько же или меньше указанной цены?

### Тесты
Перед написанием каждой функции необходимо написать тесты, которые она должна пройти: идея заключается в том, что тест — это ваш способ определить, что должно произойти, а не подтверждение после выполнения. Это можно сделать с помощью ИИ. Например, мы создаём файл `functions.test.js` внутри папки `test`, где программируем тесты, который для функции `getBookById` может выглядеть так:

```javascript
import { describe, it, expect } from 'vitest'
import * as functions from '../src/functions'
импортировать данные из '../src/services/data'

const books = data.books
const users = data.users
const modules = data.modules

describe('function getBookById', () => {
 it('getBookById 1 возвращает книгу с идентификатором 1', () => {
   const response = functions.getBookById(books, 1)
   expect(response.id).toBe(1)
 });

 it('getBookById 22 возвращает ошибку', () => {
   expect(() => functions.getBookById(books, 22)).toThrow()
 });

```

Начиная с этого теста, добавьте `_describe_` для каждой из ваших функций, указав тесты, которые функция должна пройти. Запустите `npm run test` перед написанием кода для каждой функции (чтобы увидеть, какие тесты не пройдут) и снова после написания кода (чтобы увидеть, какие тесты пройдут).

Подумайте о различных случаях, которые должен охватывать каждый тест:
— Для функций, возвращающих несколько элементов (`booksFromUser`, `booksWithStatus`...): как проверить корректность возвращаемого массива, а не просто убедиться, что он имеет ожидаемую длину?
— Для параметра `averagePriceOfBooks`: Как надежно проверить десятичное значение и символ, чтобы изменение метода округления не привело к ошибке проверки на один цент?
— Для `incrementPriceOfBooks`: как проверить, что исходный массив не был изменен и что новый массив корректен?
— Что касается функции `bookExists`, которая возвращает логическое значение: какие конкретные случаи вы будете проверять, чтобы убедиться, что она не выдает ложноположительный или ложноотрицательный результат?

### Ограничения дизайна

Нельзя использовать циклы for или while. Все задачи должны решаться с помощью функционального программирования (map, filter, reduce, find...). Это не случайно: в коде, работающем с коллекциями, функции для работы с массивами более декларативны, их проще объединять в цепочки и они легче читаются другим человеком — или искусственным интеллектом — чем императивные циклы.
- Ни одна функция не должна изменять исходный массив. Если вам необходимо преобразовать данные (например, при повышении цен), верните новый массив.
Никогда ничего не кодируйте жестко!!!

## 3 - Классы

Продолжая работу над нашим приложением для продажи учебников и конспектов, мы создадим классы, которые будем использовать в приложении. Для этого упражнения мы создадим новую ветку в нашем репозитории под названием **3-classes**. Мы перенесем логику из предыдущего упражнения в объектно-ориентированную модель. Внутри `src/` создайте папку `model/`, куда будут помещены классы. Вы будете работать с шестью классами: _**Book**_, _**User**_, _**Module**_ (представляющие отдельный элемент) и _**Books**_, _**Users**_, _**Modules**_ (представляющие всю коллекцию). Каждый класс будет находиться в отдельном файле, названном в честь класса, с добавлением `.class.js`, например, `model/book.class.js` для класса _Book_.

Перед началом работы удалите файлы `src/functions.js`, `test/functions.test.js` и `test/contrato.test.js`: их функции станут методами соответствующих классов.

Отдельные классы объектов (_Book_, _User_ и _Module_) будут иметь

- Конструктор: получает данные для создаваемого объекта. Конструктор для **User** получает _id_, _nick_, _email_ и _password_. Конструктор для **Module** получает _code_, _cliteral_, _vliteral_ и _courseId_. Конструктор для **Book**, поскольку у него много полей, получит объект со ВСЕМИ полями, хотя _photo_, _comments_ и _soldDate_ являются необязательными, и если они не получены, он присваивает им пустую строку.
- метод `toString` для отображения объекта

Классы коллекций (_Books_, _Users_ и _Modules_) будут содержать:
- `data`: свойство, содержащее массив с элементами коллекции.
- **Конструктор**: инициализирует свойство с именем data пустым массивом.
Функция `populate` принимает массив с исходными данными и создает его экземпляры, загружая их в массив `data`. Она ничего не возвращает.
- `addXXXX` (`addBook` и `addUser`): принимает объект с данными нового элемента (без идентификатора) и добавляет его в массив данных. Возвращает только что добавленный элемент.
- `removeXXXX` (`removeBook`, `removeUser`): принимает идентификатор и удаляет его из массива. Функция ничего не возвращает. Если идентификатор не существует, будет выброшено исключение.
- `changeXXXX` (`changeBook`, `changeUser`): принимает объект с данными нового элемента и заменяет элемент массива полученным. Возвращает измененный элемент, и если он отсутствует в массиве, генерирует исключение.
- Функция `toString` отображает элементы массива (вызывает `toString` для каждого элемента).
- остальные методы, созданные в предыдущем упражнении (`booksFromUser`, `getUserByNick` и т. д.), больше не будут нуждаться в получении массива с данными.

Элементы массива **_data_** в каждой коллекции будут экземплярами соответствующего класса. Помните, что для использования каждого класса в других файлах, например, в `book.class.js`, необходимо экспортировать его.

```javascript
экспортировать по умолчанию класс Book {
  ...
}
```

И везде, где нам понадобится его использовать, мы будем импортировать его, например, в файл `books.class.js`:

```javascript
import Book from './book.class'
```

### Тесты

Как и в предыдущем упражнении, необходимо создать тесты до написания кода для классов, а затем проверить, проходят ли они эти тесты. Также у вас есть файл `contract.test.js`, который проверяет правильность экспорта классов. Например, файл `book.test.js` может выглядеть так:

```javascript
import { describe, it, expect } from 'vitest'

const booksFixture = [

  { id: 35, userId: 2, moduleCode: '7021', publisher: "McGraw-Hill", price: 34, pages: 116, status: "good" }

  test('конструктор создает проданную книгу', () => {
```

## Контекст

До сих пор данные хранились в `datos.js`, в памяти. Начиная с этой практики, **`datos.js` исчезает**: `books`, `users` и `modules` находятся на сервере (`json-server`, который обслуживает файл `batoibooks.json` — помните, что он находится на бэкенде и не должен быть в вашем проекте) и доступны через HTTP-запросы с помощью `fetch`.

Вся тестовая инфраструктура предоставляется вам (`src/mocks/handlers.js` и `src/mocks/server.js`, с использованием `msw`). Это не то, что вам нужно изучить в этом упражнении — это то, как тесты имитируют сервер, не требуя его реального запуска. Вам не нужно понимать это построчно, просто знайте, что это существует и почему тесты проходят без запущенного `json-server`.

## Что должен решать ваш код

Вам потребуется новый файл, **`src/services/api.js`**, содержащий прямые вызовы `fetch`: он не определяет, что делать в случае сбоя, а просто взаимодействует с сервером.

Классы `Books` и `Users` из предыдущего упражнения изменились: их методы больше не работают с `this.data` в памяти; они взаимодействуют с сервером через `api.js`. Это имеет каскадные последствия, к которым вам нужно быть готовым:

- **Все методы, выполняющие запрос, теперь являются асинхронными.** Методы `addBook`, `removeBook` и `changeBook` теперь возвращают промис. Везде, где вы ранее вызывали их синхронно, теперь используется `await`.
— Метод `populate(array)` больше не имеет смысла в текущем виде (вы больше не получаете уже созданный массив, а запрашиваете его). Замените его методом с тем же именем `fetchAll()` (в `Books`, `Users` и `Modules`), который выполняет запрос и загружает данные, возвращаемые сервером, в `this.data`.
- `Modules` также прекращает чтение из `datos.js` и запрашивает данные с сервера. Он только выполняет запросы (не добавляет, не удаляет и не изменяет данные), поэтому `fetchAll()` и его методы поиска достаточны.

Как распределить работу между `api.js` и методами в `Books`/`Users` — решать вам. Вот вопрос, который поможет вам определиться: в классах `removeBook`/`changeBook` вызывали исключение, если элемент не существовал. Если теперь сервер возвращает ошибку 404, кто решает, станет ли это исключением — `api.js` или метод в `Books`? Подумайте, что произойдет, если завтра вы измените реализацию `api.js` на другую: должна ли остальная часть приложения быть уведомлена об изменении?

Мы не будем решать эту задачу за вас, и она уже поднималась в исходных инструкциях к этому упражнению: должны ли уже имеющиеся у вас методы запроса (`booksFromUser`, `booksWithStatus`...) работать с данными `this.data`, которые уже загружены в память (после `fetchAll()`), или же они должны запрашивать новые данные с сервера при каждом вызове? Выберите один из вариантов для этого упражнения, помня, что это упрощение: единственного «правильного» ответа не существует.

Кроме того, в этом упражнении мы удалим метод `incrementPriceOfBooks`, который мы создали для практики функционального программирования, поскольку он больше не актуален для данных на сервере. Не забудьте удалить тесты, проверяющие этот метод, а также удалить его из файла `contrato-clases.test.js`.

## Тесты

**Вам дан единственный пример** в файле `books.class.test.js`: проверка успешного выполнения `addBook`, а также имитация запуска/остановки сервера (это уже сделано, не трогайте). Обратите внимание, что тест создает экземпляр `Books` и вызывает его метод `addBook` — ему все равно, как вы распределили код между классом и `api.js`, он проверяет только результат.

Рядом с примером есть комментарий, показывающий, как использовать `server.use()` для имитации неудачного запроса (500, сервер недоступен...) **только в рамках конкретного теста**. Это не полный тест — он обучает синтаксису, но решение о том, что должно произойти в вашем коде в этом случае, остается за вами.

Остальную часть кода необходимо написать перед его генерацией:

**Важный момент, не упомянутый в предыдущих упражнениях:** `fetch` не генерирует исключение, когда сервер отвечает HTTP-ошибкой, например, 404 или 500 — оно генерируется только в том случае, если запрос даже не завершается (сбой сети, DNS, заблокированный CORS). Если ваш код предполагает, что ошибку 404 можно перехватить с помощью `try/catch` вокруг `fetch`, не проверяя `response.ok` или `response.status`, он не будет работать должным образом. Протестируйте это самостоятельно, прежде чем делать какие-либо предположения.

### Когда сервер выходит из строя

Все методы, взаимодействующие с сервером (`fetchAll`, `addXxxx`, `removeXxxx`, `changeXxxx`), должны соответствовать этому требованию:

- **Если сервер отвечает ошибкой** (404, 500...) **или не отвечает** (сервер недоступен), метод **отклоняет промис**, то есть генерирует исключение.
- **Файл `this.data` остаётся точно таким же, каким он был до вызова.** Если книгу не удалось удалить на сервере, она должна остаться в `this.data`; если её не удалось создать, она не может отображаться.

Вы сами определяете сообщение об исключении и то, будет ли оно сгенерировано `api.js` или методом класса. Помните, что `fetch` не генерирует исключение, когда сервер отвечает кодом 404 или 500, и что запись `this.data` до того, как станет известно об успешном выполнении операции, — это простой способ нарушить второе условие.

### Проверка на наличие исключений в асинхронных функциях — это не то же самое, что и раньше.

До сих пор для проверки того, вызывает ли функция ошибку, вы делали следующее:

```js
expect(() => c.getBookById(2)).toThrow()
```

Это работает, потому что `getBookById` является **синхронным**: он генерирует исключение в тот же момент, когда выполняется, и именно поэтому его нужно обернуть в `() => ...` — вы сообщаете `expect`: «Выполните его сами и посмотрите, не возникнет ли исключение».

Все методы, выполняющие запрос в этом упражнении, являются асинхронными (async), и асинхронная функция **никогда не генерирует исключение напрямую**: она возвращает промис в момент вызова, и этот промис *отклоняется* позже, когда функция `fetch` отвечает. В момент вызова нет ничего, что нужно было бы перехватывать. Синтаксис меняется следующим образом:

```js
await expect(books.removeBook(999)).rejects.toThrow()
```

Здесь вам не нужна стрелочная функция (вы передаете ей уже созданный промис, а не способ его выполнения), но вам нужен `.rejects` — она указывает `expect` дождаться разрешения промиса и проверить, был ли он отклонен с ошибкой, — и именно поэтому вся строка требует `await`.

**Обратите внимание:** Если вы забудете использовать `await`, **тест все равно пройдет, даже если ваш код не генерирует никаких исключений.** `expect(...).rejects.toThrow()` также возвращает промис; если вы не дождетесь его, Vitest продолжит работу, ничего еще не проверив, и тест будет отмечен зеленым цветом как не провалившийся вовремя, а не как прошедший проверку. Это самая распространенная (и самая опасная, поскольку она не предупреждает) ошибка при тестировании асинхронного кода. Убедитесь, что каждый тест асинхронного метода имеет свой `await`, прежде чем считать его успешным.
